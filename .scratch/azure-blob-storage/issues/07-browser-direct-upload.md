**What to build:** 从媒体库主上传器选图，经 Postiz 取得上传标识和短期 SAS，将文件直传 Blob，确认成功后在当前组织的媒体库中预览。

- [x] 商户 SSO 和普通 Postiz 登录均按当前组织申请和确认。服务端决定对象键并签发单对象写授权。现有会话上下文只发给 Postiz，浏览器向 Blob 提交 SAS。
- [x] 复用 Uppy 的选择、压图和进度界面，经微软 Azure SDK 发送上传器最终提交的文件。媒体库、预览和帖子使用持久的 Blob 源站地址，上传授权到期后仍可读。
- [x] 从当前 `merchantId` 的最终 Blob 核验文件归属、类型和字节数。商户不匹配、对象缺失、分块未提交或校验失败时不登记媒体。
- [x] 从上传和确认入口做本地回归。同一成功上传重复或并发确认只产生一条媒体记录，调用方均得到同一结果。

## Answer

主上传器沿用 Uppy 文件选择、压图及进度回调。在 Azure 模式下，即使部署中配置了转码模板，也直接调用 `BlockBlobClient.uploadData`。网页用当前 Postiz 会话申请、确认，Blob 写入使用有效期为 2 小时的单对象 HTTPS 创建 SAS。响应丢失时确认重试沿用原上传标识。

申请时生成随机上传 ID，用它和原文件名、类型、大小、用途计算文件名摘要。服务端只为当前商户目录中的该文件签发 2 小时创建授权。确认携带相同字段，服务端按同一规则定位 Blob。它核验已提交对象的长度，并按 ETag 读取前 4100 字节识别格式。遇到目录在文件尾部的 TIFF，在 10 MiB 图片上限内读取完整文件。必要时用同一 ETag 就地更正响应头。媒体以申请 ID 为现有 `Media` 主键，缩略图只返回地址。

浏览器的写地址去掉 SAS 查询串，就是最终读取地址 `https://fbrdevstorage.blob.core.windows.net/postiz/dev/<merchantId>/<文件名>`。只申请就退出不会留下文件。字节提交后即可匿名读取；未确认或校验失败的文件可留在这一地址。上传授权到期后仍可确认已经提交的文件。

本地回归覆盖 Chromium 文件选择、Azure SDK 单次和分块上传、写入响应丢失、确认重试、8 个并发确认、SAS 覆盖被拒、商户隔离、类型与大小校验、TIFF 以及授权到期。使用 main 的 Prisma schema。可设置 `AZURE_CONFIRM_TEST_DATABASE_URL` 和 `AZURE_UPLOAD_TEST_CHROMIUM` 重跑数据库和浏览器用例。7 个相关测试文件的 52 项回归均通过。真实 dev 的 Blob CORS 和匿名读取按部署手册验证。

媒体库及文章封面使用仅限当前组织的按需 WebP 预览显示 TIFF。Chromium 回归覆盖 8000 × 6000 的压缩 TIFF，显示宽度为 1280 像素，源站读回的原图摘要保持一致。无法生成预览时可直接打开原文件。确认成功但响应正文中断时，网页以同一上传 ID 重试。

R2 分片授权绑定申请时的组织、对象名和 R2 上传 ID。完成请求未送达或响应中断时，主上传器用同一授权重试。服务端优先返回已登记的媒体，也可校验已提交的对象并继续登记。升级前申请但尚未完成的 R2 上传需要重新选择文件，旧授权没有可验证的组织信息。已经保存的媒体可继续通过原地址读取。

启用 R2 转码时，如果 API 在保存媒体后、启动 Temporal 工作流前重启，后续确认使用媒体 ID 恢复转码。并发确认共用同一次工作流，转码结束后返回最终媒体地址。
