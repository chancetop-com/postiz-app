# Postiz 媒体直传 Azure Blob Storage 与排程发布

Status: resolved
Created: 2026-11-25
Resolved: 2026-11-25

## Problem Statement

Postiz dev 的新附件依赖挂载在 Pod 上的上传盘。运营者希望在网页上传图片和视频，拿到可分享的预览地址，并在排程到期时继续使用同一份素材。部署方需要知道何时可以卸载旧盘，以及哪些平台还需要配置媒体域名。

同一份素材在不同渠道有不同用途。Instagram 可以引用图片地址，YouTube 需要视频字节，WordPress 的正文图片和特色图片甚至走不同接口。只验证媒体库里能打开图片，无法判断排程能否发出正确的附件。

## Solution

增加可选的 `azure` 存储方式。网页向 Postiz 申请当前组织的临时上传授权，将文件直传 Azure，再向 Postiz 确认。确认成功后，媒体库、预览和排程使用持久的 Blob 源站 HTTPS 地址。公开 API 上传、URL 导入和后台生成媒体沿用各自入口，也能将新文件写入同一组织的存储目录。

发布进程按渠道接口、发帖形式和附件类型选取传输方式。支持拉取的接口接收 Blob 源站地址，仅接收文件的接口接收字节。部署方可以用一个开关控制所有渠道的发布前自动图片处理。交付验收覆盖后端注册的全部 35 个渠道，以及 dev 在卸载上传盘后的完整流程。

## User Stories

1. 作为商户共享账户的使用者，我希望网页上传的素材归入当前 Postiz 组织，以便同一组织的运营者能在媒体库中选用它。
2. 作为通过普通 Postiz 登录进入的组织成员，我希望直接使用组织的上传能力，以便无需建立 FBR 商户身份也能添加附件。
3. 作为媒体库使用者，我希望沿用现有文件选择和上传进度界面，以便看清一批图片或视频中哪些已完成。
4. 作为视频上传者，我希望临时网络故障只重试失败的分片，以便继续同一次上传并保留已传完的部分。
5. 作为视频上传者，我希望持续失败时看到失败状态，以便重新选择文件，且媒体库只列出已完成的附件。
6. 作为组织成员，我希望确认请求重发后仍拿到同一条媒体记录，以便在响应丢失时安全重试。
7. 作为组织管理员，我希望只有申请上传的组织能确认对应对象，以便其他组织无法将它登记为自己的素材。
8. 作为运营者，我希望上传时按现有压图设置处理大图，并保留 GIF 动画，以便切换存储后仍能预期最终入库的内容。
9. 作为视频编辑者，我希望截取或上传封面后直接得到可用地址，以便把缩略图附到视频上。
10. 作为设计器使用者，我希望保存设计后得到媒体记录，以便立即在帖子里选用设计稿。
11. 作为预览链接的收件人，我希望无需登录即可读取已确认的文件，以便上传凭据过期后仍能查看素材。
12. 作为公开 API 调用方，我希望现有 multipart 上传和 URL 导入继续接受相同请求并返回约定的响应，以便现有自动化能直接使用 Azure。
13. 作为使用后台生成媒体的运营者，我希望新生成的文件也归入当前组织并可预览，以便将它们加入排程。
14. 作为多渠道运营者，我希望单图、图集、视频、封面及正文内嵌图片各自使用渠道支持的方式发送，以便排程到期时得到预期内容。
15. 作为 TikTok 运营者，我希望照片和视频都能从已验证的 Blob URL 前缀拉取，以便直接发布和发送到收件箱都可使用 Azure 媒体。
16. 作为 YouTube 运营者，我希望发布进程能从 Blob 源站分段读取并续传视频，以便卸载上传盘后仍可发送视频和自定义封面。
17. 作为运营者，我希望渠道专用的发布副本与媒体库原图分别保存，以便同一原图可以继续用于其他渠道。
18. 作为部署维护者，我希望能统一关闭主帖、评论和回复的自动图片处理，以便使用已准备好的原图，并在格式或尺寸不合规时得到原因。
19. 作为 LinkedIn 运营者，我希望仍能显式选择 PDF 轮播，以便在关闭自动图片处理的部署中发布所选文档形式。
20. 作为排程维护者，我希望能区分平台拒绝拉取与平台已受理待处理，以便修正被拒的域名或媒体，并沿用已有发布标识跟踪已受理的请求。
21. 作为 dev 运维人员，我希望先在卸载上传盘的 Pod 中验证新媒体的完整流程，以便在验收通过后准确回收旧上传盘。
22. 作为渠道应用负责人，我希望交付时拿到实际要配置的应用、URL 前缀、验证文件位置和成功标志，以便自行完成平台验证和真实发帖验收。

## Implementation Decisions

### 上传、确认与读取

- 在现有存储工厂和共享服务端存储接口中增加 Azure 选项。调用方将已授权的组织传到实际写入点，包括服务端流式上传、URL 导入、后台生成和发布副本。媒体控制器接收请求，媒体服务负责授权与确认，仓储负责登记。
- Postiz 后端为当前组织生成文件名、对象键和上传标识，签发有效期为 2 小时、仅可创建该 Blob 的 SAS。浏览器向 Postiz 发出的申请和确认携带会话及组织上下文，向 Blob 源站发出的写请求只使用 SAS。服务端持有连接字符串。
- 沿用 FBR 的公开容器直传方式。申请时仅返回上传标识和最终 Blob 的 SAS，浏览器直接将字节提交到这个 Blob。只申请就退出不会创建对象；已提交的文件从最终地址即可匿名读取，放弃确认或校验失败可能留下这个文件。首次提交后，即使 SAS 仍有效，浏览器也无法以该授权覆盖已提交的字节。
- 主上传器保留 Uppy 的选择、进度和压图行为，Azure 传输使用微软官方 `@azure/storage-blob` 的 `BlockBlobClient.uploadData`。`maxSingleShotSize` 和 `blockSize` 均为 5 MiB，SDK 在本次上传内重试临时失败的请求，进度回传给 Uppy。关闭或刷新页面后重新选文件。
- 上传按申请、浏览器直传、完成后登记三个阶段执行。服务端按已鉴权的商户、随机上传标识及申请字段生成唯一最终键；确认带回相同的原文件名、用途、类型和大小。服务端核实实际长度、按 ETag 读取字节识别格式，再用上传标识作为现有 `Media` 的主键。重复或并发确认返回同一条媒体记录。缩略图仅返回持久地址。Prisma schema 与 main 一致。
- 主上传器和设计器在确认成功后得到媒体记录。缩略图调用只返回稳定地址。公开 API 的 multipart 上传、URL 导入以及后台生成继续使用既有协议，在服务端写入 Azure。URL 导入保留远程来源校验和流式大小限制。
- dev 使用 `fbrdevstorage` 账户中与 `static` 并列的 `postiz` 容器。Azure 上传的服务参数和 Blob 路径统一使用 `merchantId`，取值为已鉴权的 `Organization.id`，商户 SSO 和普通登录使用相同的取值规则。最终 Blob 名为 `dev/<merchantId>/<后端生成的文件名>`。确认后返回 `https://fbrdevstorage.blob.core.windows.net/postiz/dev/<merchantId>/<后端生成的文件名>`。媒体库、预览、排程、发布副本与社媒拉取均直接使用 Blob 源站地址，读链接不含 SAS。

- R2 的分片授权绑定申请时的商户。完成请求或响应丢失时，浏览器沿用同一授权，服务端恢复该对象的登记，避免重新上传分片。升级前尚未完成、缺少商户授权的 R2 上传需要重新选择文件。
- 媒体库和文章封面使用已保存的媒体 ID 请求 TIFF 的首帧 WebP 预览。仅当前商户可请求转换，服务端从原始地址读取图片并限制输入大小和解码像素数。预览无法生成时，界面提供打开原 TIFF 的链接。分享、排程及发布均沿用原始文件地址。

### 从入库文件到渠道附件

Azure 入库以 R2 关闭上传后通用转码时的行为为准。网页主上传器继续按 `DISABLE_IMAGE_COMPRESSION` 决定是否压图并跳过 GIF。Azure 保存上传器实际提交的字节，确认后即可读取。入库不触发 RunPod 图片标准化、视频转码或外部转码模板。

后端和发布 worker 读取部署级 `DISABLE_PUBLISH_IMAGE_PROCESSING`，适用于所有存储方式及主帖、后续评论和回复。未设置或空字符串时启用现有处理。任意非空值均关闭处理，包括 `true`、`false` 和 `0`。关闭后使用入库图片的实际格式和字节，跳过自动缩放、重编码、格式转换和副本写入。两种设置都执行渠道校验，遇到不兼容素材时返回原因。

| 渠道或发布形式 | 自动处理开启时的行为 |
| --- | --- |
| 普通 TikTok、TikTok Business | 将入库后仍为 PNG 的图片以质量参数 100 转为 JPEG，另存发布副本。媒体库保留 PNG。 |
| X | 普通帖图片等比调整到宽 1000 像素并转 GIF，文章封面及内嵌图按同样宽度转 JPEG。 |
| LinkedIn 个人及主页 | 普通 GIF 原样发送。其他图片缩至 6000 × 6000 范围内，小图不放大。PNG、JPEG 以原格式重编码，其他可处理格式转 JPEG。显式选择的 PDF 轮播在开关两种状态下均生成文档。 |
| Bluesky | 976 KiB 以内的图片原样上传。超限时每轮将宽高缩至上一轮的 90% 并重编码，直至达到大小目标或尺寸下限。 |
| 其余渠道 | 保留既有的元数据读取、封面、附件或正文引用规则。Kick、Twitch 和 Moltbook 验收现有文字发布与回复。 |

按具体平台接口、帖子形式和附件逐项固定传输方式。平台支持 URL 拉取时提交持久 Blob 源站地址和所需元数据，避免为转发而下载完整文件。仅接受文件时由发布进程读取适用版本并上传，按接口续传或引用平台返回的媒体 ID。一个帖子的视频与封面可走不同接口。现有代码采用字节上传的分支仍须核实该接口是否支持 URL。

普通 TikTok 在 Azure 模式下，图片和视频在直接发布和发送到收件箱时均采用 `PULL_FROM_URL`。TikTok Business 使用其发布接口的 URL 字段。拉取被拒时保留平台错误和修正方向，`url_ownership_unverified` 指向媒体前缀验证。发布时不探测域名验证状态，也不自动改传字节。已受理的请求沿用原发布标识查询结果，重试沿用同一种传输方式。

### dev 部署与旧盘退役

| 位置 | 配置 |
| --- | --- |
| `postiz-config` | `STORAGE_PROVIDER=azure`、`AZURE_CONTAINER=postiz`、`AZURE_BASEPATH=dev`。需要关闭发布前处理时设 `DISABLE_PUBLISH_IMAGE_PROCESSING=true`。 |
| `postiz-secret` | 从 dev 的 file-service 加密配置取得同一存储账户的 `AZURE_CONNECTIONURL`，按目标 Secret 的 SOPS 规则保存，通过运行环境供后端和需写媒体的任务进程使用。 |

环境负责人先确认账户允许匿名 Blob 访问，`postiz` 容器访问级别为 `blob`。持链接者可匿名读取单个文件，列出容器内容需要授权。Blob 服务的 CORS 规则须允许 dev 网页来源发送 SDK 直传所需的 PUT 和请求头。

在 `fbr-env-project` 分两次切换。先核对 dev 集群，记录 `dev/postiz-uploads-pvc` 绑定的 PV、回收策略和 Azure Disk 资源 ID。部署支持 Azure 的版本，移除本地上传目录设置、上传卷挂载和对应 volume，保留 PVC。确认 rollout 成功、无 Pod 引用旧上传 PVC，再从 dev 网页验证 Blob 跨域写入和 Blob 源站匿名读取。

无盘验收通过后再移除旧上传 PVC 声明并回收对应的 10 GiB 磁盘。`Retain` 时核对 PV 已释放、磁盘 ID 相符且已脱离挂载，再回收 PV 和磁盘；实际策略为 `Delete` 时核对自动回收结果。操作对象仅限已核对的上传盘。未来切回 `local` 且需要持久存储时须重新提供上传卷。

## Testing Decisions

验收使用已确认的两个边界。上传从调用方能使用的入口开始，核对返回结果及从 Blob 源站实际读回的内容。发布从排程的媒体准备和渠道发送入口开始，核对模拟平台实际收到的请求及返回给排程的状态。断言可观察的记录、字节、地址、错误和发布标识，无需为每个内部方法另建测试接口。

| 边界 | 验收场景与通过条件 |
| --- | --- |
| 上传入口及返回值 | 覆盖主上传器、缩略图、设计器、公开 API multipart、URL 导入和后台生成。核对各自的响应形状、组织归属，以及新文件位于对应组织的 Blob 前缀。持链接者在无会话且上传 SAS 已过期后仍能读取，Content-Type 与文件相符。 |
| 上传格式与 R2 对照 | 按现有媒体库白名单覆盖 JPEG、PNG、GIF、WebP、AVIF、BMP、TIFF、MP4。按入口验证图片 10 MiB、视频 1 GiB 的适用上限及越界拒绝。在 Azure 与 R2 关闭外部转码模板，用相同的大图、GIF 和视频分别跑压图开、关两组。对照是否压图、最终格式与尺寸，并逐次比对实际提交文件与各自公开地址读回文件的摘要（Azure Blob 源站、R2 既有 CDN）。 |
| 确认与重试 | 覆盖组织不匹配、对象缺失、未完成、内容与申报不符、格式不支持及超限。重复和并发确认只产生一条记录。让大于 5 MiB 的视频某一分片首次收到 503，确认只重传失败分片，进度最终完成且从 Blob 读回的摘要一致。持续失败到重试耗尽时界面提示失败，媒体库无记录。 |
| 35 个发布渠道 | 以全部后端注册标识为清单，包括界面隐藏、dev 未绑定的标识和同品牌的不同接入。按逐渠道矩阵为每个标识记录适用形式、预期 URL 字段或上传字节、成功和错误结果。覆盖单图、图集、视频、封面、正文内嵌、主帖、评论和回复；纯文字渠道记录文字回归及媒体不适用项。 |
| 发布前图片处理 | 用 PNG、GIF、WebP 和超限图片覆盖开关未设置、空值、`true`、`false`、`0`。核对实际发出的格式、尺寸或字节，以及 TikTok 副本和媒体库原件的去向。关闭时验证原图发送、渠道拒绝不合规原图并给出原因、显式 LinkedIn PDF 轮播仍可生成。 |
| 模拟平台通信 | 用 Instagram 核对单图、轮播和视频封面的 URL。用普通 TikTok 核对两种发布模式的照片和视频拉取、前缀拒绝及已受理待完成。用 YouTube 核对视频 HEAD、Content-Length、Range 206、续传字节和自定义封面。用 WordPress 核对正文引用及特色图片 ID。拒绝拉取后无字节回退，已受理后沿原标识跟踪。 |

仓库中的 Nest HTTP 上传测试、上传会话请求头测试和媒体库测试已分别覆盖入口响应、组织上下文与前端完成状态。公开读取测试已有文件字节与 Range 断言。TikTok 披露测试通过模拟平台捕获普通版、Business 版的真实出站请求体。Azure 回归沿用这些方式，并在确认幂等用例中保留实际登记行为。

dev 验收在未挂载上传盘的 Pod 中重跑上述上传与读回流程，覆盖每种支持的媒体类型、中断重试和公开 API、导入及后台生成入口。发布回归同样在无上传盘条件下运行。先保存实际环境的验收结果，再进入旧盘回收。各渠道真实发帖由用户自行安排。

## Out of Scope

- 历史本地媒体迁移、旧 `/uploads/` 链接兼容、旧排程修复及数据库记录批量清理。旧盘下线后，引用旧文件的预览和排程可能失败。
- Azure 入库后的通用图片重编码、视频转码，以及刷新或关闭页面后的跨会话断点续传。
- 代用户向社媒实际发帖，或代查普通 TikTok 应用后台的域名验证状态。
