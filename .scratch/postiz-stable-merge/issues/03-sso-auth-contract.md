## Question

面对稳定版鉴权变化，怎样逐项保留父应用 iframe 内无需二次登录、商户身份及组织关联，并明确哪些现有实现必须维持、哪些可以调整？

讨论必须基于三方证据和真实场景：
- 旧入口 /auth/sso?token、新入口 /sso?auth_code、SSO_TOKEN postMessage、完整 SSO_SERVER_URL 与验证请求/响应格式；旧文档“URL 自动追加 /api/sso/verify”与源码不一致。
- 现有 Provider.GENERIC + merchantId 身份查找、已有用户/组织复用、首次自动创建；文档的 create-account/needsCreation/父页成功失败消息尚无实现，究竟是过时设计还是需要额外确认的业务目标？
- auth/showorg/impersonate 响应头与 sessionStorage、CORS、普通登录/注册/激活/OAuth、组织切换、管理员代入、退出、401；上传与 Copilot 等绕过统一 fetch 的请求同样覆盖。
- 后端仍兼容 cookie、代理不再基于 cookie 拦截、客户端 /user/self 校验等实现如何与新版整合；不能把 iframe 可用的目标直接等同于必须保留每个旧实现细节，也不能默认允许替换。
- 旧文档“不修改父应用代码”的约束怎样落实到实际外部接口；SSO 失败、用户已存在、组织缺失、换商户/换标签页等边界。
- token 有效期与来源校验等差异只在具体兼容问题中讨论，不借升级默认开展全面鉴权重构。

答案应逐项给出保留/适配/待确认结论及验收场景，并记录用户对争议项的真实答复。

## Comments

- 2026-11-11：[身份、鉴权与共享工具证据](../assets/customization-auth-evidence.md) 与 [前端行为证据](../assets/customization-frontend-evidence.md) 已完成 B/C/S 核对；以下是需用户逐项决定的事实输入，不是决议。
- 稳定版的**登录 OAuth**新增 state cookie 校验，现有统一 fetch 去掉默认 credentials include；跨 origin API 与第三方 cookie 受限场景需具体讨论。自动合并还留下 AuthController 的 `getCookieUrlFromDomain` 缺失导入，必须在执行时修复，不能靠“无文本冲突”放行。
- GENERIC 同时供标准 OAuth 与 merchantId 使用，schema 没有 providerId+providerName 唯一约束；需要确认旧身份来源是否共存。SSO 明确选择未排序的第一个组织，会覆盖新版无显式组织时的订阅组织优先逻辑；禁用成员、无组织、多组织情形仍需用户定义。
- 稳定版新增账户删除/凭据交换；与现有 SSO 自动开户组合后，同商户重新进入可能建立全新账户和组织，需明确是否符合业务意图。现有数据是否实际触及这些情形尚无证据。
- 统一 fetch、Uppy、主布局/Agent/预览 Copilot 的 auth/showorg/impersonate 覆盖并不一致；退出、旧 cookie、同标签换商户需要逐路径验收。旧 SSO 页面同步读取 searchParams 也需在目标 Next 版本验证。

### 2026-11-11 本轮对话与当前约束

- 用户选择继续本地图；本轮开始时由 chancetio (agent wayfinder_sso_auth_contract) 认领。

- 会话问题的原提案同时包含了现状（标签页各自保存会话）和新增修复（重新进入 SSO 前清除旧身份，失败不再沿用旧商户）。用户起初选择建议，随后追问是否与以前一致；代理明确说明新增清理不是已有行为。

## Answer

2026-11-11，经本票记录的真实问答解决。**保留现有 SSO 和整站鉴权行为；删除账户、永久交换登录身份仅隐藏界面入口，代码与接口保留。** 此为兼容规划，未实施产品合并或代码变更。

### 保留与适配边界

| 范围 | 决议与执行约束 |
| --- | --- |
| 父应用契约 | 保留 `/auth/sso?token` 转接、`/sso?auth_code` 和 SSO 页既有 `SSO_TOKEN` 消息入口；URL code 优先、消息监听时机和现有来源配置按当前行为保留。父应用不改代码，不新增持续监听切商户或父页成功/失败通知协议。 |
| 兑换服务 | 保留完整 SSO_SERVER_URL、POST `{auth_code}` 及 merchant_id/merchant_name 映射；不自动拼接路径、不增独立开户接口或 needsCreation 分支。现有成功/失败呈现及跳转以当前源码为准，实际外部兑换行为由证据票核实。 |
| 商户账户 | 保留 GENERIC + merchantId 查找、同商户共享身份、已有账户复用、首次自动创建用户及组织；首次组织角色保持当前 SUPERADMIN，不能混同全局管理员。现存数据身份不重绑，不默认新增命名空间迁移或并发开户策略。 |
| 组织 | 保留当前查询及 orgs[0] 选择、现有手动切换、成员有效性检查与回退行为；已有用户缺组织时不自动补建。稳定版订阅组织优先等语义差异不能无意改变现状；以旧/新同样场景对照确认，不自行改成新的绑定、排序或选择规则。 |
| 会话 | 保留 sessionStorage 的 auth/showorg/impersonate、响应头非空覆盖、当前 cookie 兼容及优先级、各标签页各自保存状态的方式。**不新增 SSO 开始或失败时清空旧会话**，也不新增全标签同步、会话有效期、来源校验策略。渠道弹窗沿用现有专用会话传递，具体流程交给渠道票。 |
| 登录与页面鉴权 | 保留普通邮箱登录/注册/激活、标准 OAuth 登录、独立窗口访问及 iframe 的 SSO 免登录目标。保留现有客户端 `/user/self` 检查与 proxy 分工；不恢复会阻断 iframe 的 cookie 页面门禁。普通登录/OAuth 的独立窗口验收与社交渠道授权分开。 |
| 退出、401、代入和旁路请求 | 按当前具体路径保留，不统一重写。管理员代入继续保留；停止代入未清 sessionStorage、旧 cookie/组织残留、Uppy/Copilot 请求头不齐等现存缺口仅记录，不借升级修复。原有 401、退出、网络错误、预览例外分别与基线对照，不能笼统宣称所有错误都跳登录。 |
| 删除账户 | **所有账户界面均无删除入口**，包括普通账户、商户账户及新版设置等可见入口；删除功能源码、路由、接口行为保留，不增加后端禁用逻辑。这不是 API 不可调用的承诺，直接调用接口仍按上游逻辑处理。 |
| 永久交换登录身份 | **所有界面均无此功能入口**，包括管理员界面；相关源码及接口保留、不改。不能因此隐藏或禁用现有管理员代入，也不能把永久凭据交换混称为代入。 |
| 必要技术适配 | 可处理目标版本 API/类型/导入变化及冲突组合，以维持上述行为；例如缺失 cookie helper 导入、旧 SSO 页 searchParams 与目标 Next 版本的兼容。登录 OAuth 的上游 state 往返校验须完成兼容，不以删除该校验解决 cookie 问题。技术适配不是批量改写身份/会话策略的授权。 |

### 验收场景

1. 三个既有 SSO 入口分别覆盖首次商户、已有商户、无/无效 code、远端失败；父应用调用形式不变，成功复用或开户及失败呈现与基线一致。
2. 相同存量用户、组织和成员数据覆盖单组织、多组织、首组织禁用、全部不可用、缺组织及手动切换；比较选定组织和实际请求组织，不能因上游回退差异静默改变归属。
3. 同标签页 A→B、B 认证失败、旧 showorg/impersonate/cookie 共存、刷新、新开/复制标签页及渠道 popup 分别对照。既有残留缺口应列为基线事实；不把本票撤回的清理方案写成通过条件。
4. 普通登录、注册、激活和标准 OAuth 在独立窗口回归，iframe SSO 在目标浏览器及 cookie 限制下回归；检查请求/响应头和 CORS，以及 OAuth state 在真实 origin 布局下往返。
5. 普通退出、401、`/auth/logout`、组织切换、开始/停止管理员代入、上传、主布局/Agent/预览 Copilot 分路径验证；区分旧有问题、合并回归和缺条件未验证。
6. 普通用户、商户用户与管理员的桌面/移动相关页面均没有删除账户或永久交换凭据的可操作入口；界面隐藏可保留组件源码。审阅接口差异，确认没有为本决议新增后端禁用/拒绝逻辑或删除路由；现有管理员代入入口和行为保留。
7. 保留的删除/交换接口仍具有上游行为，不能将“界面隐藏”报告为功能彻底禁用。若验证接口行为，只在获准的本地/测试副本内进行，不对真实账户或数据库执行。
