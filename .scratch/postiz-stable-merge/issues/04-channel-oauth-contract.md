## Question

如何在完整接入稳定版 provider 与回调流程的同时，保留 iframe 内连接渠道的完整体验和现有可见渠道范围？

逐项明确：
- iframe 打开 popup → hash 携带会话信息 → channel-relay 设置 popup 会话 → 外部 OAuth → 完成页发 CHANNEL_UPDATED → opener 刷新并关闭 popup 的每一步。
- 普通浏览器路径、多账号选择、重连、取消/失败、popup 被阻止、opener 丢失等如何判定完成或失败。
- 现有六个 identifier：youtube、linkedin、tiktok、facebook、instagram、instagram-standalone；白名单目前只限制添加渠道前端列表，不代表后端其它 provider 禁用。
- 稳定版新增 provider/identifier 与上述产品限制冲突时的具体取舍。
- 当前 targetOrigin=*、接收者不校验 origin/source、relay redirect 无校验；根据父应用不改动的约束逐项讨论兼容方案，不暗自保留缺陷或批量重写。
- 每项能用 mock 验证的场景与必须真实平台 OAuth 才能验证的场景分别列明。

## Comments

- 2026-11-11：[前端逐项证据](../assets/customization-frontend-evidence.md) 已核实实际分支和稳定版改动，本票仍未决。
- `CHANNEL_UPDATED` 不只在成功时发送，412/406 分支也会通知并关闭；需要先定义它代表“刷新”还是“连接成功”。其它失败、多步保存、弹窗被拦截或 opener 丢失有不同路径。
- popup 定制仅覆盖 AddProvider 的特定分支；重连仍直接改当前 location，invite/mobile/Web3/extension 也有其它分支。要明确 iframe 必保范围，而不是默认添加成功覆盖所有流程。
- 稳定版增加 `tiktok-business`、`tumblr`；现有六 identifier 过滤不含它们，也不含 `linkedin-page`，且不限制 article 列表、后端 provider 或存量渠道。需明确“六 identifier”与“六个平台家族”的含义。
- 手工 SSO 测试页监听的消息名与当前 `CHANNEL_UPDATED` 不一致，不能作为已通过的回传验收；中转、来源校验、重复 popup flag 与错误反馈需另定具体场景。

### 2026-11-11 最终澄清：保留整个 flow

- 用户答复：**“既然没有冲突不就能直接合并吗，我说的行为不变是指原来的整个flow”**。
- 这解释并覆盖代理此前将“行为不变”扩大为冻结所有旧内部细节/异常分支的做法。保留对象是两个 commit 建立的完整使用流程；没有破坏 flow 的上游变化直接纳入，无需逐项征询。
- 因此402中止、账号/密钥类provider重连表单、新版时区处理按兼容上游更新纳入方案，不再作为三项待用户批准的决定。402拒绝时不再继续无效授权，不被要求复刻旧版的后续解析；仍须验证正常授权能完成，拒绝不会污染会话或破坏后续正常操作。
- 若验证发现实际 flow 不兼容，先做维持 flow 的技术适配；确实无法兼容时，展示原有行为、新版变化及具体冲突交用户评估。本轮据此解决本票，不扩大为立即执行产品合并或上线。

## Answer

2026-11-11，经用户最终澄清解决。**保留两个 commit 建立的完整 flow：父应用内免二次登录进入 → 现有六个添加入口 → iframe 弹窗携带会话 → 外部授权及必要的账号选择 → 回调通知原页面刷新并关闭弹窗。父应用接口、身份/组织归属和已定界面范围保持兼容；不破坏这一 flow 的上游更新直接纳入，不要求每个内部实现或旧异常分支完全相同。** 只有确实无法维持 flow 的具体冲突才交用户评估。未执行合并、产品代码修改或上线。

### 可见渠道范围

| Identifier | 保留的渠道入口 |
| --- | --- |
| `youtube` | YouTube |
| `linkedin` | LinkedIn 个人账号 |
| `tiktok` | 现有 TikTok 接入 |
| `facebook` | Facebook Page |
| `instagram` | Instagram (Facebook Business) |
| `instagram-standalone` | Instagram (Standalone) |

- 这是六个精确 identifier，Instagram 有两种接入方式；不能按“平台家族”自动扩大到 `linkedin-page` 或 `tiktok-business`。稳定版 `tiktok-business` 的添加列表名称也叫 TikTok，不能用显示名称代替 identifier 判断。
- `linkedin-page`、`tiktok-business`、`tumblr` 及其它非白名单 provider 不提供可见添加入口；保留其代码、注册、路由和接口，不增加后端禁用，也不删除或停用已有绑定。
- “其他界面不显示”的范围是本轮讨论的渠道添加/选择入口。验收须检查社交、文章以及新版可能提供的其它添加入口；旧代码仅过滤 social 不能证明整个添加界面已满足要求。此条不授权隐藏存量渠道管理、删除存量数据或改变已绑定渠道的发布行为。

### 弹窗与授权行为

| 范围 | 保留契约 |
| --- | --- |
| iframe 添加渠道 | 保留现有受覆盖分支的 popup → hash 会话传递 → channel-relay 写入 popup sessionStorage → 外部 OAuth → callback → opener 刷新/关闭链路；父应用不用改代码。auth/showorg/impersonate 传递继续按 [SSO 与整站鉴权契约](03-sso-auth-contract.md#answer) 保留。 |
| 其它入口 | 普通窗口添加和六项普通 OAuth 重连继续使用当前窗口导航，不借升级改为 popup。上游账号/密钥类provider的重连表单、Web3编码、扩展兼容等直接纳入，不扩大可见渠道；不能把一次添加成功解释为所有入口均已运行验证。 |
| 多步选择 | 保留现有中间选择页、单选及保存流程，不扩展为批量绑定多个账号；需要中间选择时不提前通知并关闭。当前六项中的 YouTube、Facebook Page、Instagram (Facebook Business) 要分别覆盖此流程。 |
| 回传语义 | 保留 `{ type: 'CHANNEL_UPDATED', provider }`、接收后刷新列表以及现有回传/关闭顺序。200/201 完成、二步保存成功、412 与406 都可能回传，所以消息只表示需要刷新，不能当作连接成功证明。成功必须结合接口结果与实际绑定状态判断。 |
| 取消与失败 | 保留完整授权与回传flow，接受不破坏它的上游错误处理，包括402拒绝后停止继续解析/授权；不要求复刻每个旧异常分支。现有其它回调失败不回传、二步失败可能继续显示选择器等作为基线证据；平台取消需实际验证，不假设全部取消等于一个状态码，也不擅自开展本次上游之外的错误体验重写。 |
| popup 生命周期 | 弹窗被阻止、opener 丢失、关闭失败、relay 缺参数、重复操作或遗留 popup flag 等按基线对照；既有未处理路径只记录，不擅自加回退页、自动重试、flag 清理或新的父页通知协议。 |
| 当前校验方式 | targetOrigin=`*`、接收端只检查消息 type、relay redirect 无校验等当前实现保留，不把增加 origin/source/redirect 校验作为此次升级默认工作。这是保留边界，不是对这些路径安全性的验证结论。 |
| 新版时区与其它兼容更新 | 纳入newDayjs用户时区处理、账号/密钥重连表单、402中止及其它不破坏flow的上游更新；这些不再单独待批。保留本地会话传递、六项入口、popup及回传链，不用旧文件覆盖新版全部实现。 |
| 必要适配与用户评估 | 类型、导入、框架或新版provider/callback的技术适配以维持上述完整flow为目标，自行解决不改变flow的冲突。仅在确实无法兼容、必须改变定制体验或已定范围时，记录具体入口、旧/新行为、复现证据、已排除的办法和备选影响，交用户决定。 |

### 验收与证据边界

1. **界面与代码审阅**：添加渠道的社交/文章及新版入口只提供六项；按 identifier 校验，特别防止同名 TikTok 新 provider 被放入。检查其它 provider 源码、注册和接口仍保留，存量绑定没有被隐藏要求误删或禁用。
2. **本地 mock / 浏览器桩**：分别对照 iframe 添加、普通窗口、重连及各早退分支；验证 hash 会话传递、relay 写入、回调选择器、保存、刷新与关闭的顺序。覆盖200/201、412、406、其它错误、二步成功/失败；收到 CHANNEL_UPDATED 不等于成功。
3. **异常与flow完整性**：覆盖402拒绝、弹窗拦截、opener缺失、close失败、relay缺参数、重复操作/遗留flag及二步失败。新版402停止后续授权是预期更新，不算定制回归；确认正常授权仍能完成，拒绝未污染会话或破坏后续操作。其它差异按是否破坏完整flow及是否超出上游更新范围判断，不要求每个旧异常分支逐句一致，也不把静态分析当成已修复。
4. **真实 OAuth**：六项分别验证实际同意页、重定向往返、回调、拒绝/取消、需二步选择的账号/页面选择、保存后绑定状态以及重连。iframe 与独立窗口、真实 origin 和目标浏览器的 cookie/popup 限制均需真实环境证据；mock 无法证明平台配置、授权权限或跨站流程可用。
5. **无可用外部条件时**：明确写“未验证”及缺少的账号/平台配置/父页环境，不把静态检查或旧测试页当成真实授权成功。当前手工 SSO 页消息名不一致，不能拿它直接验收 CHANNEL_UPDATED。
6. **分类交接**：分别列出现有问题、合并新增问题、缺外部条件未验证。合并新增问题应在保持契约的前提下解决；必须改变上述行为才能继续的具体阻塞，先由用户评估。
